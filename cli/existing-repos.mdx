---
title: "Work on an existing repo"
description: "Map a local codebase and make changes you can review with Git."
---

<Steps>
  <Step title="Start in the checkout">
    ```bash
    cd my-existing-app
    predev
    ```

    The current directory is the workspace. The CLI associates it with a pre.dev project and resumes that association on later launches. `--new` creates a fresh association.
  </Step>
  <Step title="Map the architecture">
    Accept the existing-codebase analysis prompt when offered, or run `/reverse`. Inspect the result with `/arch`. Rerun analysis after major structural changes when the stored architecture needs refreshing.
  </Step>
  <Step title="Describe a change">
    ```text
    Fix invoice date formatting for non-US locales. Preserve the
    existing timezone handling and add a regression test.
    ```

    Use `/plan` if you want to develop the approach first. For separate workstreams, use `/sprint` or `/fork` with a clear task description.
  </Step>
  <Step title="Inspect the result">
    ```bash
    git status
    git diff
    ```

    Read the reported tests, review changes in the active checkout or session worktree, and resolve any conflicts before committing or merging. Request the commit, PR, or review behavior you want explicitly in the task.
  </Step>
</Steps>

Project planning artifacts are also available in the web workspace. Local and hosted code still follow your repository's synchronization workflow. For a hosted checkout, use [GitHub import](/coding-agent/projects/importing-repos).
