Build a small issue board, add a useful filter, and inspect the result. You can follow the same workflow in a new project or an existing repository.

## Before you start

You need a [pre.dev account](https://pre.dev) and available [credits](/coding-agent/plans-and-credits). To work on existing code, have access to the GitHub repository you want to import.

## Build your first change

<Steps>
  <Step title="Create a project">
    Sign in at [pre.dev](https://pre.dev) and describe what you want to build, or [import a GitHub repository](/coding-agent/projects/importing-repos).

    ```text
    Build an issue tracker for a small design team.
    Include projects, assignees, due dates, and a status board.
    Start with a working board using sample data.
    ```
  </Step>
  <Step title="Choose how to start">
    The agent chooses the next step itself: it can build a small change directly or plan a larger one first. To work on the requirements and architecture first, ask for a plan in your message.

    For an existing app, include the expected behavior, the current problem, and any files or constraints you already know.
  </Step>
  <Step title="Connect what the project needs">
    Open `/integrations` for **Project setup**. Choose the relevant connection account, enable skills or MCP servers, and fill required **Env Vars**. Use [environment settings](/coding-agent/integrations/env-vars) for secrets and configuration.
  </Step>
  <Step title="Build a concrete change">
    Ask the agent to implement the first useful piece. For a dedicated sprint, use:

    ```text
    /sprint add filtering by assignee and status, with an empty state
    ```

    A useful result lets you combine both filters, shows only matching issues, and explains when no issues match. Include these criteria in your request so you can check them in the preview.

    Follow the active session and its progress. Additional web sessions may require a connected GitHub repository.
  </Step>
  <Step title="Review and ship">
    Inspect the code changes, reported checks, and available preview. Test your acceptance criteria, then request any corrections. Use your project's GitHub and deployment workflow to ship the reviewed result.

    The session **Merge** action can create a pull request and merge it automatically when clean. Use a review-first request if you want a PR left open.
  </Step>
</Steps>

## Check the result

Select an assignee and a status, then clear each filter. Try a combination with no matching issues. Compare that behavior with the code changes and the agent's verification report.
